# Localization and Internationalization

BC Arcade uses `i18next` + `react-i18next` with namespace files loaded through
`i18next-resources-to-backend`.

This document is the source of truth for the localization architecture,
supported locales, formatting rules, contributor workflow, and known RTL
limitations.

## 1. Supported locales

`frontend/src/i18n/locales.js` is the product-level source of truth for the
locale roster.

| `en` | English | English | LTR | Yes | Yes |
| `fr-CA` | French (Canadian) | Français | LTR | Yes | Yes |
| `es` | Spanish | Español | LTR | Yes | Yes |
| `hi` | Hindi | हिन्दी | LTR | Yes | Yes |
| `ar` | Arabic | العربية | RTL | Yes | **No — pending native RTL support** |
| `zh` | Chinese (Mandarin) | 中文 | LTR | Yes | Yes |
| `ja` | Japanese | 日本語 | LTR | Yes | Yes |
| `ko` | Korean | 한국어 | LTR | Yes | Yes |
| `pt` | Portuguese | Português | LTR | Yes | Yes |
| `he` | Hebrew | עברית | RTL | Yes | **No — pending native RTL support** |

| `ru` | Russian | Русский | LTR | Yes | Yes |

There are therefore:
- **13** supported translation locales on web;
- **11** locales exposed by the native language picker in dev, e2e and
  pre-launch builds;
- **3** locales — `en`, `fr-CA`, `es` (`LAUNCH_LOCALE_CODES`) — in **store
  builds** on every platform, for the v1 US + Canada launch (#3150). The others
  stay translated and CI-checked but are not offered to store users until they
  get the same correctness review (#3152).

Older backlog references to “14 locales” are historical and should not be used
as the current roster.

## 2. RTL status

Arabic and Hebrew translation files exist and are loadable on web.

Web:
- `useHtmlAttributes()` keeps the root `<html lang>` and `dir` attributes in
  sync with the active i18n locale;
- Arabic/Hebrew therefore render in an RTL document direction.

Native:
- `I18nManager.allowRTL(false)`;
- `I18nManager.forceRTL(false)`;
- `NATIVE_LOCALES` filters Arabic and Hebrew from the picker.

This is intentional until #2212 implements and verifies native RTL layout.
Do not claim Arabic/Hebrew native support merely because their translation files
exist.

## 3. Locale selection

At application startup:

1. Expo Localization returns the device's ordered locale preferences.
2. `resolveLocale()` walks them in order.
3. An exact supported language tag wins first.
4. Otherwise the app tries a base-language match (for example a device French
   locale can resolve to `fr-CA`).
5. Otherwise the app falls back to English.

The set considered depends on platform and build (`availableLocales()`):
- web → all `LOCALES`;
- native → `NATIVE_LOCALES` (RTL locales excluded today);
- store builds → the above, filtered to `LAUNCH_LOCALE_CODES`. Dev, e2e
  (`EXPO_PUBLIC_TEST_HOOKS=1`) and pre-launch-API builds keep everything —
  `SHOW_UNLAUNCHED_LOCALES` uses the same predicate as `SHOW_HIDDEN_GAMES`.
  A device whose only preference is a hidden locale resolves to English.

### Manual language switch

The language picker calls `i18n.changeLanguage(code)`.

Current behavior is **runtime-only**: the chosen override is not separately
persisted by BC Arcade. On a fresh app process/start, locale initialization is
resolved again from the device preference list.

If persistent in-app language preference is added later, document:
- storage key;
- precedence over device language;
- reset/follow-system behavior.

## 4. English fallback

i18next is configured with:

`fallbackLng: "en"`

If a requested locale/namespace/key is absent, English is the fallback language.

This is a resilience mechanism, **not** permission to ship silently incomplete
translations.

The loader/test contract is designed to prevent a file from merely existing on
disk while never being loaded.

## 5. Namespaces

`frontend/src/i18n/localeLoaders.ts` owns the namespace roster and explicit
Metro import table.

Current namespaces are:

- `common`
- `yacht`
- `cascade`
- `blackjack`
- `twenty48`
- `solitaire`
- `freecell`
- `hearts`
- `sudoku`
- `feedback`
- `profile`
- `starswarm`
- `mahjong`
- `sort`
- `daily_word`
- `daily_challenge`
- `result`
- `leaderboard`
- `stats`

Metro requires literal dynamic-import paths, so every locale/namespace file must
be explicitly represented in `localeLoaders`.

Adding a JSON file without adding its loader is a bug: i18next can quietly show
English fallback even though the translated file exists.

## 6. Translation metadata

`frontend/src/i18n/locales/_meta/*.meta.json` contains translator-facing
metadata for keys, including where applicable:

- component/context;
- description;
- tone;
- character limit;
- interpolation placeholders;
- values that must not be translated;
- notes.

The English locale defines product meaning; metadata explains how that meaning
should be translated rather than forcing translators to infer intent from a
short key.

When adding a user-facing key, add/update the metadata for that namespace when
context, constraints, placeholders, or non-translatable terms matter.

## 7. Interpolation and plural forms

Use i18next interpolation rather than string concatenation for translatable
sentences.

Pluralized strings must provide the CLDR categories required by each locale.
The test suite verifies the plural forms used by the project's locale roster and
the platform/polyfill behavior.

Do not assume every language only needs singular/plural English forms.

Placeholders must remain structurally consistent with the English source and
metadata.

## 8. Numbers, dates, and time

Visible formatting should follow the **app's active language**, not merely the
device's language.

### Numbers

Use the shared `formatNumber(t, value)` helper.

It builds `Intl.NumberFormat` with the language currently used by the
translation function and falls back to English if Intl rejects the locale.

### Dates and timestamps

Use `formatDate(t, ...)` / `formatTimestamp(t, ...)`.

These deliberately combine:
- **app language** for formatting conventions;
- **device local timezone** for the instant's displayed local time.

Do not replace these helpers with bare `toLocaleString()` /
`toLocaleDateString(undefined)`, because those follow device language and can
disagree with the language the user is seeing in the app.

### Durations and percentages

Use translated units/templates (for example Profile's hours/minutes and percent
strings), not English suffixes assembled in code.

## 9. Server vs client copy

The backend should prefer language-neutral data contracts where practical.

Examples:
- Daily Challenge sends `game_type + kind + target`; the client localizes the
  goal.
- Leaderboard/Stats APIs return values/labels through generated/product
  vocabulary rather than localized sentences.
- Game result state is translated on the client.

Do not add server-generated English copy to an otherwise language-neutral API
without an explicit reason.

## 10. Daily Word

Daily Word is distinct from the app UI locale system because the puzzle itself
has a language.

Its game specification owns:
- which puzzle languages are supported;
- puzzle/word validation behavior;
- how puzzle language is selected.

UI chrome around Daily Word still uses the normal i18n namespaces.

Do not infer that adding an app locale automatically creates a Daily Word puzzle
language.

## 11. Daily Challenge

Daily Challenge goal text is localized on the client in the
`daily_challenge` namespace.

The wire contains goal semantics, not prose. Unknown future goal kinds degrade
to generic localized fallback wording rather than exposing a raw translation
key.

The challenge's **calendar-day calculation is not a localization feature**.
Timezone/day semantics live in [DAILY-CHALLENGE.md](DAILY-CHALLENGE.md).

## 12. Accessibility strings

Visible text and accessibility-only labels are both localization scope.

Examples include:
- button labels;
- VoiceOver/TalkBack action descriptions;
- modal labels;
- state announcements;
- screen-reader-only text.

Do not fix visible copy while leaving a hardcoded English
`accessibilityLabel` behind.

The accessibility interaction contract itself remains in
[ACCESSIBILITY.md](ACCESSIBILITY.md).

## 13. Automated enforcement

Important current checks include:

### `localeLoaders.test.ts`
Verifies:
- namespace list matches English files;
- loader-table locales match configured locales and directories;
- each locale loads every JSON file it owns;
- loaders point at the correct locale path;
- no `__NEEDS_TRANSLATION__` placeholders remain;
- English fallback behaves as expected.

### `locales.test.ts` / `resolveLocale.test.ts`
Verify:
- locale configuration;
- native RTL filtering;
- locale resolution/fallback behavior.

### plural tests
`pluralForms.test.ts` and `pluralRulesPolyfill.test.ts` protect CLDR plural
behavior.

### string audit
`frontend/scripts/check-i18n-strings.js` audits locale structure/content using
the English files and `_meta` metadata.

Treat these checks as enforcement of the translation-file contract. They do not
replace human/native-speaker review of wording quality.

## 14. Adding a key

1. Choose the correct namespace; do not put game-specific copy in `common`
   merely for convenience.
2. Add the English key/value.
3. Add/update `_meta/<namespace>.meta.json` when translator context is needed.
4. Add the key to every locale with the correct placeholders/plural forms.
5. Use `t()` in visible and accessibility copy.
6. Run the i18n/string/plural tests.
7. Check compact layouts for languages whose text expands significantly.

## 15. Adding a namespace

1. Add the English JSON file.
2. Add the namespace to `NAMESPACES`.
3. Add a literal loader entry for **every supported locale** in
   `localeLoaders`.
4. Add the namespace's translated JSON to every locale.
5. Add metadata where applicable.
6. Run `localeLoaders.test.ts` and the string audit.

The tests intentionally fail when a file/loader/locale set drifts.

## 16. Adding a locale

1. Add it to `LOCALES` with code, English label, native label, flag, and
   direction.
2. If RTL, decide whether native support is actually implemented before exposing
   it through `NATIVE_LOCALES`.
3. Create the locale directory with every namespace JSON.
4. Add literal namespace loaders for the locale.
5. Supply all required plural forms/placeholders.
6. Run all localization tests and the string audit.
7. Manually review Home, Settings, Profile, shared result/reporting surfaces,
   and representative games.
8. For RTL, verify directional icons, board/game semantics, and native/web layout
   separately.

## 17. Translation provenance / review

`locales/provenance.json` exists for translation provenance where tracked.
It is not a substitute for source strings, metadata, or review.

Machine-assisted translation may accelerate coverage, but product-critical,
ambiguous, culturally specific, or space-constrained copy should be reviewed in
context. Automated tests catch structure; they do not prove a translation is
natural or correct.

## 18. Known open work

- **#2212** — native RTL support. Until this lands, Arabic/Hebrew are web-only.
- **#855** — broader localization coverage/quality audit. Its historical

  13-locale / 12-game repo rather than treated as present-day inventory.

## 19. Ownership rules

- Locale roster/direction → `i18n/locales.js`.
- Platform availability / initial resolution → `resolveLocale.ts`.
- Namespace roster/loaders → `localeLoaders.ts`.
- Runtime initialization/fallback → `i18n.ts`.
- Translator context → `locales/_meta/`.
- App-language number/date formatting → shared formatting helpers.
- Native RTL capability → #2212 / platform implementation.

When localization architecture changes, update this document and the relevant
tests in the same PR rather than duplicating the rules in release plans.
